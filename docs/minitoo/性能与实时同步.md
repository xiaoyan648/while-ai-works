# MiniToo 真机性能与实时同步 · 2026-09-21

设备：用户的 Divoom MiniToo-Audio，固件 2.4.0；本地 arm64 原生应用。桌面游戏关闭，设置窗口打开。保留手动「鱼缸 / Codex」选择，不自动切换。

## 真机结果

用户已确认 Codex 页面正常、文字清楚。同步鱼缸能够显示，但第一版移动太快；据此放慢到 48 帧 × 200 ms = 9.6 秒一轮，最大水平移动速度从约 61 像素/秒降到约 16 像素/秒，掉头采用横向收窄过渡。新动画获得设备最终 ACK，主观游动观感尚待用户反馈。

| 情况 | 结果 | 测量口径 |
| --- | --- | --- |
| 原版六条鱼首次开启，24 帧 / 595 包 | 约 17 秒 | UI 操作时间到设备 ACK，含首次连接；起点为近似值 |
| 新版 Codex 冷启动 | 3.80 秒 | 准备开始到 ACK，包含蓝牙连接 |
| 新版 Codex 连续更新 | 多数 0.23–0.35 秒，中位约 0.28 秒 | 原生单调时钟，准备开始到最终 ACK |
| 从鱼缸切到 Codex 的首张图 | 约 1.11–1.14 秒 | 包含设备切换接收状态的等待；随后恢复约 0.28 秒 |
| 新版六条鱼，48 帧 / 300,741 字节 / 1,176 包 | 约 7.46–7.47 秒 | 准备开始到 ACK；帧数已增加，不能据此声称严格同图倍数 |
| 日志事件写入到状态模型更新 | 21–110 毫秒，六次 | 隔离的本地文件测试，非模型端生成耗时 |

连续更新和切换测试累计至少 23 次 Codex 上传、2 次鱼缸上传均获得最终 ACK；5 ms 包间隔未触发降速。关闭时成功发送熄屏指令，重新开启获得 Codex ACK；鱼缸上传期间选择 Codex，最终显示模式与最后选择一致。没有自动切换显示内容。

ACK 表示设备确认接收，不等同于测得液晶实际刷新时刻。没有摄像机逐帧测量，也没有把预计的端到端耗时冒充实测。任务完成/中断用本地生命周期测试覆盖，本轮真实会话尚在运行。

## 已落地的改进

1. 保持 RFCOMM 长连接，仍按 256 字节协议分块；写完成回调后等待 5 ms 再发下一包。遇到失败后手动重试降到 20 ms，仍保留超时与最终确认。
2. 首次亮屏保留 0.5 秒等待；已亮屏时不重复发亮屏命令和等待。
3. 用系统文件事件监听 Codex 日志，100 ms 合并突发写入；保留 1.5 秒轮询作为兜底。最多监听 48 个日志文件和 24 个目录；目录事件发现新任务，正常兜底发现间隔仍为 6 秒。
4. 相同画面不重绘预览、不编码和不发送；上传进度最多每秒发布十次，减少界面刷新。
5. 同一时间只上传一份内容，中途修改只保留最新选择，不排长队、不混包。

文件事件方案使用 [Apple DispatchSource 文件监听接口](https://developer.apple.com/documentation/dispatch/dispatchsourcefilesystemobject)。设备的 256 字节分块和较短包间隔参照 [MiniToo 协议研究](https://github.com/bugzmanov/divoom-minitoo/blob/main/FINDINGS.md)，最终以本机 ACK 测量为准。

## 更实时同步的调研结论

**当前优先采用“日志事件触发 + 小状态图 + 持久蓝牙连接”。** 已知会话的日志事件到设备确认预计可接近数百毫秒，但还受 Codex 写日志时机、设备忙碌和当前上传影响。运行时长仍按十秒粒度变化，避免为了秒表持续占用蓝牙；运行/完成状态事件不需要等十秒。

**Zstandard RGB 压缩暂不引入。** 社区已验证其他 MiniToo 图像路径，要求限制解码窗口；错误窗口可能收到 ACK 却显示异常。[协议说明](https://github.com/alvinunreal/divoom-minitoo-osx/blob/main/PROTOCOL.md)。本机对同一 160×128 Codex 示例 PNG 离线压缩，固定 window_log=17，level 3/9/19 含头分别约 7,081 / 6,949 / 5,563 字节；现用真实 Codex JPEG 通常约 5.6 KB，优势有限。这不是同一画面的严格 JPEG 对比，也未验证 160×128 Zstd 真机展示，因此不为此增加应用运行时依赖。

**预存表盘切换适合少数固定状态，不适合动态会话列表和额度。** 公开项目报告部分固件在切换存储表盘后忽略后续实时图片，需要重新启动设备。[Divoom Stats 说明](https://github.com/estlin/divoom-stats#known-behavior-last-frame-stays-on-quit)。本轮不修改用户表盘槽位。

**尚未找到在本机验证过的局部矩形更新或通用实时 framebuffer 接口。** 当前发送的仍是完整小图，不能把缓存动画的播放帧率当作实时交互帧率。后续若确需持续刷新，先用同画面比较压缩和端到端延迟，再评估；不靠提高轮询频率或更换连接名称解决。
