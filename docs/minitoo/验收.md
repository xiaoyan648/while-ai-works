# MiniToo 鱼缸展示验收 · 2026-09-20

设备：Divoom MiniToo-Audio，固件 2.4.0；Mac 蓝牙已配对。此次验证使用本地原生 arm64 应用，未发布安装包。

## 已完成

- 设置界面音量下方有「MiniToo 鱼缸展示」开关、预览、连接状态与重试；实际运行界面已检查。
- 在「开始玩」关闭时，独立开启 MiniToo 鱼缸。
- 通过原生 IOBluetooth 的 RFCOMM channel 1，上传 138,635 字节的 24 帧动画，共 543 个包。
- 23:14:46 本机日志记录 `upload acknowledged (543 packets)`，只有收到设备最终 ACK 后才显示“设备已接收”。
- 用户目视确认：“看到了，小鱼在正常游动”。
- 关闭设置开关后用户目视确认：“屏幕已经熄灭”。此固件没有回复熄屏 ACK，因此正常写入完成后提示“已发送熄屏指令”，与动画上传的最终 ACK 区分。
- 最终构建再次开启时收到设备完整动画 ACK；再次关闭时设置显示“已关闭 · 已发送熄屏指令”，不再误报传输失败。
- 握手改进后的最终版本：首次打开收到上传 ACK，随后完成“关闭 → 保留控制通道 → 再开启 → 再次收到上传 ACK”，无需手动重试。验收结束时开关保持开启。
- 应用重启恢复已开启的设置；首次授权由用户在 macOS 系统弹窗完成。
- `bash scripts/check-minitoo.sh` 通过：固定协议向量、碎片/损坏接收流、24 帧 JPEG 解码、分块重组、准备阶段取消、两种异步写回调 selector。
- `bash scripts/check.sh` 通过：CoreChecks 46、FishingChecks 191，原生交互、声音、素材、三维鱼和设置/图鉴渲染检查。
- `codesign --verify --deep --strict 'dist/While AI Works.app'` 通过。

## 测试中修复

1. 首次蓝牙授权期间，直接在主线程调用 IOBluetooth 配对查询导致等待。改为 CoreBluetooth 异步授权后再在后台初始化 IOBluetooth，并提供超时与权限提示。
2. 此 macOS 使用旧版 `rfcommChannelWriteComplete:refcon:status:`；只实现带 `bytesWritten:` 的版本会导致只发送首包。现已兼容两种回调，并在检查中验证 selector 存在。
3. 关闭后反复重新打开 RFCOMM 会出现连接成功但不回应。开关改为保留健康控制通道、切换屏幕，退出应用时再释放连接。
4. 增加亮屏后的 0.5 秒等待、一次受限的握手重试，以及写回调序号匹配，避免重复或过期回调影响后续数据包。
