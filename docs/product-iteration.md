# 需求整理与持续迭代

本页记录 WAW 的需求筛选方法和首轮候选，供维护者整理 Issue、已授权读取的用户反馈及主动脑暴。产品边界以 [Product](../PRODUCT.md) 为准：帮助用户留意 AI 的工作，在等待时短暂放松，随时回到工作。

## 参考 magpie 的做法

参考项目为 [yetone/magpie](https://github.com/yetone/magpie)，以下结论来自公开仓库，不代表已接入它的自动化系统。

- **把反馈变成可复现的问题。** [PR #1324](https://github.com/yetone/magpie/pull/1324) 从 Issue 的空会话分页问题出发，记录旧实现失败、新实现通过的验证。
- **说明用户能观察到的变化。** [子系统文档约定](https://github.com/yetone/magpie/blob/7af2a18c975a1d2fba93aedf17f556a3b0abf830/docs/subsystems/README.md) 要求描述触发条件、修改前后行为、接口和失败路径，并更新对应设计文档。
- **复盘返工，积累证据。** [Lessons](https://github.com/yetone/magpie/blob/7af2a18c975a1d2fba93aedf17f556a3b0abf830/LESSONS.md) 记录每日复盘方法：检查哪些修改又被修正、哪些验证不足，再把反复出现的教训整理进规范。

WAW 采用反馈、验证、交付、复盘的闭环。发布频率取决于有效改动和验收结果，不以每天新增功能或发布版本为目标。

## 每日整理方法

1. 读取上次成功整理之后新增或更新的 Issue、PR，以及已授权反馈来源。首次运行建立基线；分页读完后再记录读取时间。来源不可访问时记为「未读取」，不能当作没有反馈。
2. 按用户问题合并重复反馈，核对当前版本、已有实现、在途 PR 和发布记录。已修复的问题只在新版本仍可复现时重新进入候选。
3. 沿「接入 AI → 等待 → 处理提问或审批 → 回到会话 → 放松」脑暴。每个想法写明谁在什么场景遇到什么阻力，并标记为假设；没有新证据时可以不新增候选。
4. 用下表判断价值，优先处理阻断现有流程且能复现的问题。为选中的需求写明最小改动、验收场景和不包含的内容。
5. 在独立分支实现聚焦改动，按 [开发说明](../CONTRIBUTING.md) 运行相关检查。UI 改动保存相同场景、视口、主题和状态的 Before / After 实际应用截图，并标明版本。
6. PR 记录行为变化、实际验证和限制；合并与发布沿用项目现有权限。向反馈来源交付可审阅结果，不将 PR 创建等同于发布完成。
7. 复盘最近完成的修改：是否又返工、是否漏掉调用路径、验证是否覆盖真实使用。记录证据及下次如何避免；没有证据时不新增规则。

## 每日触发

使用 DSH 原生「自动化任务」将本流程绑定到专用会话，规则为每天北京时间 10:00（`daily.time = "10:00:00"`、`daily.time_zone = "Asia/Shanghai"`）。创建前检查同名任务，创建后回读任务名称、规则、状态和下次触发时间，避免重复配置。任务及私人反馈来源保存在本机，不随仓库分发；克隆仓库不会自动创建任务。

DSH Host 需要运行才能投递任务；停机期间无法准时执行，恢复后每项周期任务只补最近一次错过的触发。自动化记录中的投递成功仅说明消息进入会话，不能代替需求整理、代码检查或 PR 交付成功。首次到点后需检查会话执行结果，之后按日期和来源游标去重。

## 怎样判断需求有价值

| 判断项 | 需要记录的证据 |
| --- | --- |
| 产品相关性 | 是否改善现有 AI 等待、介入、返回会话或桌面放松流程；是否符合 Product 中的边界 |
| 用户影响 | 是否阻断任务、丢失输入、误导状态，或只是偏好；受影响的使用场景 |
| 证据强度 | 可复现反馈、多个独立反馈、单个反馈或纯脑暴；不要编造用户数量 |
| 当前替代方案 | 用户现在如何完成，绕行成本是什么；是否已有实现或在途 PR |
| 改动成本与风险 | 能否局部解决；是否涉及客户端兼容、隐私、权限、数据迁移或多模块职责调整 |
| 可验证性 | 怎样确认问题消失，怎样检查旧流程没有退化 |

候选状态使用「待验证 → 已选定 → 实现中 → 待审阅 → 已交付」。证据不足可暂缓，重复或不符合产品方向可不采纳，并保留原因。会改变产品方向、已有调用约定或多个模块职责的方案先做明确决策，不因实现行数少就直接推进。

## 需求记录模板

```text
标题：
来源与时间：（脑暴明确写“假设”）
用户与场景：
当前行为 / 期望行为：
影响与证据：
已有实现 / 重复需求 / 替代方案：
决定与理由：
最小范围与不包含内容：
验收场景：
状态 / PR / 发布版本：
下一次验证需要什么：
```

公开记录只保留适合公开的事实。飞书中的私人对话、账号、截图、日志和凭据留在有权限的原始来源；需要公开复现时使用合成数据。不要直接复制群聊内容到 Issue 或 PR。
